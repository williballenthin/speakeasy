# Issue template for automated VT-audit findings

Model issue: https://github.com/williballenthin/speakeasy/issues/21 (and #22–#50 from the first audit). Match its depth and tone. A maintainer who has never seen the sample should be able to understand the defect, judge whether to fix it, and reproduce it.

Rules:
- Title: one sentence that states the defect and its consequence, for example "snapshot_memory_regions never captures heap memory, so payloads that loaders unpack into HeapAlloc buffers are missing from the report". No "[vt-audit]" prefix; the label covers that.
- Label: `vt-audit`. Make the issue a sub-issue of the run's summary issue.
- Every claim comes from this run's evidence: traces, disassembly, code you read at the audited commit. If something is inferred (for example "Windows would do X"), say so.
- Defang network IOCs (`hxxp://`, `1.2.3[.]4`, `example[.]com`). Never attach or paste sample bytes beyond short disassembly.
- Code references are repo-relative `path/file.py:line` at the audited commit, so name the commit.
- Keep listings ≤ ~30 lines each.
- End the body with the attribution footer.

python -m speakeasy -t <sample> --max-run-time 30 --max-api-calls 20000 -o report.json

## Details
- The speakeasy code that does the wrong thing (a short excerpt in a fenced block, with `path:line`).
- Disassembly of the relevant guest code (address, bytes or mnemonic), with comments.
- An excerpt of the API trace (API, args, return value) that leads to the failure.
- Tables are welcome for comparisons (e.g. "in stock report? no").

## Impact
What the sample does once this is fixed, if you tested a monkeypatch: APIs reached, payload strings, C2. Otherwise what it would do. Say how general the issue is: one family, or a class of loaders.

## Suggested fix
The smallest generic change, not a per-family handler. Describe any monkeypatch you tested and its before/after. List alternatives, and reasons a maintainer might decide not to fix it.

## Test case
- Sample-based regression: the command or library call, the run limits, and the assertion (e.g. "run reaches API X", "no invalid_protect_write at pc Y", "string Z appears in memory").
- Synthetic test without malware, if one can show the bug (tests/pe_builder.py, handler harness): a sketch.
